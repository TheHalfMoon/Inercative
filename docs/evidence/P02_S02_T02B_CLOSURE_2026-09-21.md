## 3. What was delivered

The domain layer of `@ineractive/product-graph` now carries data-governance relations and cross-node
rules:

- an **endpoint-pair table** as the single endpoint authority, with the declared `from`/`to` sets
  derived from it, so a relation name can hold source-specific targets without widening an endpoint
  set into combinations earlier Grains rejected;
- the `classified_as` relation (`entity -> dataclass`);
- `governs` accepting `permission -> action` and `datapolicy -> entity`;
- `requires` accepting `requirement -> datapolicy`;
- the `governance` phase after `relation` with three stable error codes:
  `DOMAIN_CONFLICTING_CLASSIFICATION` (an entity classified into more than one level),
  `DOMAIN_SENSITIVE_DATA_WITHOUT_POLICY` (classified `personal`, `sensitive`, `secret`, or
  `regulated` with no governing policy), and `DOMAIN_CLASS_POLICY_CONFLICT` (a policy that allows
  continuous export while governing `secret` or `regulated` data).

Only structurally admissible relations participate in governance: a `governs` edge that already
failed endpoint validation cannot make an entity governed, which keeps the rule fail-closed rather
than dependent on a malformed document.

## 4. Preserved rejections

The alternative implementation — widening `governs` to `from: [permission, datapolicy]` and
`to: [action, entity]` — was declined because it would silently accept `permission -> entity` and
`datapolicy -> action`, both of which earlier Grains reject. The endpoint-pair table preserves every
previous rejection, and an explicit table test pins `permission -> entity`, `datapolicy -> action`,
`permission -> datapolicy`, `datapolicy -> dataclass`, `entity -> entity`, and `page -> page`.
